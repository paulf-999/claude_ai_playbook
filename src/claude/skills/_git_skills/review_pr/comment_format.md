## Scoring guides

**Theme scores (1–10):**

| Score | Meaning |
|:---|:---|
| 9–10 | Excellent — sets the bar |
| 7–8 | Good — meets the bar with minor gaps |
| 5–6 | Acceptable — works but has notable gaps |
| 1–4 | Needs work — significant issues before merging |

**Overall score:** average of the five theme scores, rounded to one decimal place.

**Grade mapping:**

| Score | Grade |
|:---|:---|
| 9.5–10 | A+ |
| 9.0–9.4 | A |
| 8.5–8.9 | A− |
| 8.0–8.4 | B+ |
| 7.5–7.9 | B |
| 7.0–7.4 | B− |
| 6.5–6.9 | C+ |
| 6.0–6.4 | C |
| 5.5–5.9 | C− |
| 5.0–5.4 | D+ |
| 4.0–4.9 | D |
| < 4.0 | F |

**Verdict determination (pass to the agent) — based solely on Must items:**

| Verdict | `<verdict>` | `<verdict_emoji>` | Condition |
|:---|:---|:---|:---|
| Approve | `Approve` | ✅ | No Must items AND no Should items |
| Approve with suggestions | `Approve with suggestions` | 💬 | No Must items, but Should/Could items present |
| Request changes | `Request changes` | ❌ | Any Must item present |

The overall score does not determine the verdict — Must items do.

**Header bullet guidance (pass to the agent):**
- Write 1–3 bullets in plain English for a mixed technical/non-technical audience
- Do not repeat scorecard detail — these bullets convey the overall signal only
- **For Request changes:** cover only the Must items. State what must change before this can merge. Be direct — do not soften. Omit Shoulds from the header entirely.
- **For Approve with suggestions:** lead with why the PR is safe to merge, then briefly note what the Should items cover so the reader knows what to expect in the detail below.
- **For Approve:** explain briefly why it is safe to merge (logic sound, no breaking changes, no concerns).
- Aim for 1–2 bullets; add a third only if there is a materially distinct point that does not fit elsewhere.

**Summary guidance (pass this to the agent):**
- Think theme and intent, not file names or implementation — "what problem does this PR solve?" not "what does it add?"
- If the PR has multiple distinct themes, pick the dominant one for bullet 1 and use bullet 2 for context or impact
- Avoid phrases like "This PR adds...", "This PR introduces..." — lead with the capability or outcome instead
- Where a specific file is naturally referenced, link it: `[filename](repo_url/blob/headRefName/path/to/file)`

**Recommendations guidance (pass this to the agent):**
- Format as a table with three columns: Theme, Severity, Recommendation
- **Theme**: an emoji followed by a short label for the category of concern — choose an emoji that reflects the theme (e.g. `🧪 Eval quality`, `⚠️ Error handling`, `🔗 Integration`, `📝 Docs`). Bold the whole cell: `**🧪 Eval quality**`
- **Severity**: one of **Must** / **Should** / **Could** / **Want** — capitalised, rendered as bold (not code). Meaning:
  - **Must** — blocking; should be addressed before merge
  - **Should** — important but not blocking
  - **Could** — worthwhile improvement, low priority
  - **Want** — nice to have; optional polish
- **Recommendation**: use `•` bullets with `<br>` between them so each bullet renders on its own line. Link any referenced files or keywords using `[text](url)`. At minimum one bullet; add a second if there is meaningfully distinct detail to include.
- Omit the section entirely if there is nothing to recommend

**Notes field guidance (pass this to the agent):**
- 1–2 bullets per cell using `•` as the bullet character and `<br>` between bullets so each renders on its own line
- Each bullet: bold keyword + colon + brief plain-English point (e.g. `• **Clarity**: Easy to follow and well-structured`)
- Plain English — assume a mixed technical and non-technical audience
- High-level observations only — avoid specific line numbers or implementation detail
- Where a specific file is naturally referenced, link it: `[filename](repo_url/blob/headRefName/path/to/file)`

**Testing row guidance (pass to the agent):**
- Score the 🧪 **Testing** row based on: whether tests exist for the changed code, whether test coverage is appropriate for the change type, and whether any test files are included or updated in the diff
- If the PR is configuration, documentation, or tooling with no testable logic, note this and score accordingly (e.g. 9/10 — not applicable)
- If tests are absent where they would be expected, score low and flag in Recommendations

**Linking rules (pass to the agent):**
- Construct file links as: `{repo_url}/blob/{headRefName}/{filepath}` for files on the PR branch
- Only link files that are actually changed in this PR — do not link files not in the diff
- Link the shortest natural anchor text (e.g. `[SKILL.md](url)` not `[src/claude/skills/review_pr/SKILL.md](url)`)
- Do not force links where none fit naturally — link only when a specific file is being directly referenced
